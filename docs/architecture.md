# Task Tracker Architecture

## 1. What the app does

Task Tracker is a learning-focused web application for creating, retrieving, listing, filtering, partially updating, moving between permitted statuses, and deleting tasks.

The application consists of:

- A FastAPI REST backend.
- A task-board frontend implemented in a single vanilla HTML/CSS/JavaScript file.
- A process-local, in-memory Python dictionary used for task storage.

The API supports:

- `POST /tasks` to create a task.
- `GET /tasks/{task_id}` to retrieve a task.
- `GET /tasks` to list tasks, with optional status, priority, and overdue filters.
- `PATCH /tasks/{task_id}` to partially update a task.
- `DELETE /tasks/{task_id}` to delete a task.
- `GET /health` for a health response.
- `GET /` for basic API and environment information.

Task data is not persistent and is lost when the backend process restarts.

## 2. Data model

The central entity is a task. Pydantic models define the create, update, and response shapes:

- `TaskCreate` defines accepted creation fields and their defaults.
- `TaskUpdate` defines the fields accepted by a partial update.
- `TaskResponse` represents a complete stored and returned task.

| Field | Behavior |
|---|---|
| `id` | Decimal string generated by the storage layer from the current dictionary size plus one |
| `title` | Required on creation; trimmed, nonblank, and limited to 200 characters |
| `description` | Optional on creation; stored as an empty string when absent or `null` |
| `status` | `ToDo`, `InProgress`, or `Done`; defaults to `ToDo` |
| `priority` | `Low`, `Medium`, or `High`; defaults to `Medium` |
| `assignee` | Optional string; defaults to `null` |
| `due_date` | Optional date |
| `tags` | List of strings; defaults to an empty list |
| `created_at` | Backend-generated UTC timestamp |
| `updated_at` | Backend-generated UTC timestamp, refreshed when a non-empty update is applied |

Request models reject unknown fields.

For a non-null title supplied on creation or update, leading and trailing whitespace is removed. The title must remain nonblank after trimming and cannot exceed 200 characters.

Tags must be provided as a list of strings. Each tag is trimmed, empty tags are discarded, and duplicates are removed case-insensitively. The spelling and order of the first occurrence are preserved.

Overdue status is computed rather than stored. A task is overdue when:

- It has a due date.
- Its due date is earlier than the current local date.
- Its status is not `Done`.

A task due today is not overdue.

## 3. Request flow

For task creation, the frontend validates and trims the title, parses the tags, builds a JSON payload, and sends `POST /tasks`.

FastAPI parses the request body as `TaskCreate`. Pydantic validates the supplied fields, rejects unknown fields and invalid enum values, applies defaults, and normalizes the title and tags.

The route delegates the validated model to `storage.add_task()`. The storage layer:

1. Generates an ID from the current number of entries plus one.
2. Creates UTC `created_at` and `updated_at` timestamps.
3. Constructs a `TaskResponse`.
4. Inserts the task into the module-level dictionary.

The API returns the created task with HTTP 201. After a successful create or edit request, the frontend requests the task list again and redraws the board.

For listing, `GET /tasks` accepts optional `status`, `priority`, and `overdue` query parameters. The storage layer combines any supplied filters and sorts the result by creation timestamp in ascending order. In the current frontend, status and priority filters are applied in the browser, while the overdue selection is also sent to the API.

For updates, FastAPI parses the body as `TaskUpdate`. Only fields explicitly supplied in the request are applied. An empty update returns the existing task unchanged. When a status is supplied, the API validates the transition before updating storage.

The permitted status transitions are:

- `ToDo` → `InProgress`
- `InProgress` → `Done`
- `Done` → `InProgress`

All other status transitions, including assigning the current status again, return HTTP 422.

The frontend also uses `PATCH` to edit task fields and move tasks by drag and drop. It uses `DELETE` to remove tasks.

## 4. Key files

- `app/main.py` — Creates the FastAPI application, configures CORS, includes the health router, exposes task CRUD endpoints, and delegates persistence operations to the storage layer.
- `app/models.py` — Defines task request and response models, status and priority enums, defaults, title validation, and tag normalization.
- `app/storage.py` — Implements process-local in-memory CRUD operations, ID generation, filtering, creation-time sorting, and overdue calculation.
- `app/business_rules.py` — Defines and validates the permitted task-status transitions.
- `app/core/config.py` — Loads the application environment and port from environment variables, with development and port `8000` defaults.
- `app/api/routes/health.py` — Provides `GET /health`, returning an `ok` status and a UTC timestamp.
- `frontend/index.html` — Contains the complete task-board markup, styling, forms, browser-side filtering, drag-and-drop behavior, validation, rendering, and API requests.
- `tests/test_tasks.py` — Contains tests for task creation, retrieval, listing, filtering, partial updates, status transitions, tags, deletion, and error responses.
- `tests/conftest.py` — Provides the FastAPI test client and resets in-memory storage around each test.
- `docs/decisions/in-memory-task-storage.md` — Records the decision to use temporary in-memory storage and describes its persistence and multi-instance trade-offs.

## 5. Conventions

- **API style:** Task operations use JSON over REST with `POST`, `GET`, `PATCH`, and `DELETE`.
- **Validation:** Request models forbid unknown fields. Pydantic validates field types, enum values, and dates. Non-null titles are trimmed and checked for blank or excessive length. Tags are normalized before storage.
- **Partial updates:** Omitted fields are preserved. A request with no supplied update fields returns the existing task without changing its `updated_at` timestamp.
- **Business rules:** Status changes must follow the transition rules in `app/business_rules.py`.
- **Storage:** Tasks are held in a module-level dictionary and disappear when the process restarts.
- **Identifiers:** IDs are decimal strings calculated from the current dictionary size plus one. This is a simple prototype convention rather than a persistent or concurrency-safe identity strategy.
- **Ordering:** Listed tasks are sorted by `created_at` in ascending order.
- **Overdue calculation:** Overdue status uses the backend’s current local date and excludes completed tasks.
- **Errors:** Missing task IDs return HTTP 404. Request validation and invalid status transitions return HTTP 422. Successful deletion returns HTTP 204 with no response body.
- **Frontend/backend interaction:** The frontend uses `fetch` and refreshes the task list after successful mutations.
- **CORS:** The backend permits the configured local development origins on ports 5500 and 5173, as well as the `"null"` origin.

## 6. Not visible or assumptions

The following are not confirmed by the inspected repository files:

- A database, ORM, or persistent storage system.
- Authentication or authorization.
- A frontend framework, build tool, or JavaScript package manager.
- A production deployment topology.
- Durable or coordinated behavior across multiple backend processes.
- Concurrency guarantees for task creation or updates.
- A production-ready ID-generation strategy.

The verified local host port is 8001, matching frontend/index.html. Docker intentionally maps host port 8001 to the container’s internal port 8000.

The test files document expected behavior, but the tests were not run as part of this architecture review. No current passing-test result is claimed.

## Context Strategy Comparison

### Strategy A - Minimal Context

#### What it got right

Strategy A produced a concise but broad description of the complete application. It correctly identified:

- The FastAPI backend and vanilla HTML/CSS/JavaScript frontend.
- The in-memory and nonpersistent storage model.
- The task fields, enums, timestamps, and computed overdue behavior.
- The creation flow from frontend submission through Pydantic validation and storage.
- The roles of the main backend, frontend, test, configuration, health, and decision-record files.
- Browser-side status and priority filtering versus the overdue query sent to the API.
- The mismatch between the frontend’s port 8001 and the backend configuration’s port 8000.

Its strongest feature was density: it included most important architectural facts without becoming long.

#### What it got wrong, invented, or missed

Strategy A did not contain a major invented component, but some statements were less precise than the repository supports:

- It described the application as supporting “editing” and “moving” without explicitly connecting moving to the permitted status-transition rules.
- Its validation summary said titles are required without distinguishing creation from partial updates.
- It did not list the permitted status transitions in the conventions section.
- It omitted `tests/conftest.py`, which is architecturally relevant because it resets the module-level storage between tests.
- It did not mention the empty-update behavior.
- It did not call out the limitations of generating IDs from dictionary size, including the absence of concurrency or durable uniqueness guarantees.
- It said CORS permits “configured local development origins” but did not identify those origins.

These are primarily omissions or precision issues, not fabricated repository facts.

### Strategy B - Structured Context

#### What it got right

Strategy B was the most complete and well-organized of the three drafts. It correctly added or made explicit:

- A field-by-field task model table.
- The create, update, and response model roles.
- The permitted status transitions and the rejection of same-status updates.
- Partial-update preservation of omitted fields.
- `tests/conftest.py` and its storage-reset role.
- The API’s 404 and 204 behavior.
- The frontend’s forms, filters, drag-and-drop behavior, and API calls.
- The absence of a database, ORM, authentication, frontend framework, package manager, and confirmed production architecture.
- The port mismatch between the frontend and backend setup.

Its structured context provided the best balance between backend implementation, frontend behavior, tests, and supporting documentation.

#### What it got wrong, invented, or missed

Strategy B was accurate overall, but it still had several gaps or statements needing qualification:

- Its general statement that titles are trimmed and constrained did not distinguish non-null title validation from the fact that `TaskUpdate.title` is optional.
- It did not mention the empty `PATCH` behavior.
- It did not describe the root or health endpoints even though it listed their supporting files.
- It did not state the exact CORS origins.
- It did not explain that the overdue calculation uses the backend’s current local date.
- It did not discuss the limitations of calculating IDs from the dictionary size.
- It referred to the setup instructions when discussing port 8000. That conflict is supported by repository context, but the architecture itself is clearer when tied directly to `app/core/config.py` and the hard-coded frontend URL.

These are mostly missing details. No database, service, or other architecture component was invented.

### Strategy C - Targeted Context

#### What it got right

Strategy C was strongest where it stayed close to the backend files it had inspected. It accurately described:

- The API’s task CRUD operations and list filters.
- The task fields and Pydantic model roles.
- The `POST /tasks` flow.
- Unknown-field rejection and title and tag normalization.
- In-memory storage, creation-time ordering, ID generation, and overdue calculation.
- Missing-task handling in the API layer.
- The exact categories of permitted CORS origins.

It also correctly labeled information outside its inspected context as not visible instead of inventing details. That is a sound evidence-handling practice.

#### What it got wrong, invented, or missed

Most of Strategy C’s weaknesses were caused by restricted context rather than false repository claims:

- It could not describe the permitted status transitions because it had not read `app/business_rules.py`.
- It could not describe the health endpoint or environment configuration because it had not read their implementations.
- It omitted the existing frontend’s filename, request behavior, browser-side filtering, editing, deletion, and drag-and-drop features.
- It omitted the test suite’s visible coverage and storage-reset fixture.
- It omitted the storage decision record and its documented trade-offs.
- It treated validation-response behavior as not visible even though tests could have confirmed it with broader context.
- Its “What the app does” section described only the REST service, leaving out the repository’s working frontend.
- It did not expose the port mismatch because it had not inspected both frontend and configuration sources.

These are supported-context omissions, not inventions. Its caution was appropriate, but the resulting document was too incomplete for a repository-level architecture overview.

### Verdict

I would choose **Strategy B - Structured Context** for this architecture task.

It produced the most useful repository-level architecture because it combined implementation, frontend behavior, tests, configuration, and decision documentation while preserving a clear section structure. Strategy A was impressively concise but missed several important conventions and qualifications. Strategy C was disciplined about evidence, but its targeted context was too narrow to describe the complete application.

The best final result uses Strategy B as the foundation, Strategy A’s concise explanation of the end-to-end frontend request flow and port mismatch, and Strategy C’s discipline of marking genuinely unconfirmed architecture as not confirmed.
